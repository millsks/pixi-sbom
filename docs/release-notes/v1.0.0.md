## 1.0.0

pixi-sbom generates a CycloneDX or SPDX Software Bill of Materials from a `pixi.lock`. It has done
that since 0.1.0. What 1.0 adds is a promise about it.

### What the promise is

[What 1.0 freezes](https://millsks.github.io/pixi-sbom/latest/stability/) lists it exactly: 65
command-line flags, 29 configuration keys, 9 exit codes, 11 environment variables, 54 `pixi:*`
document names, and the GitHub Action's inputs and outputs. None of those change without a major
version.

It is just as specific about what is **not** covered — log lines, table layout, recommendation
wording, element ids and ordering, cache layout, the published Rust library. If something in your
CI parses one of those, it was never a contract and this is the release that says so out loud.
Gate on exit codes.

That page is checked against the code on every commit. A flag added without a line on it fails the
build, and so does a line on it for a flag that no longer exists. The list cannot quietly drift
from the binary, which is the usual fate of a document like this.

### Nothing was removed to get here

Two flags were renamed for consistency with the ones beside them:

| Pre-1.0 | Now |
|---|---|
| `--name` | `--root-name` |
| `--outdated-only` | `--outdated-min` |

**Both old spellings still work, and always will.** So does `--pypi-licenses`, deprecated since
0.4.0. Removing an alias in 1.0.0 would have been a breaking change shipped as the release whose
whole point is that we stop breaking people; keeping one costs two lines and a test. If any of
them ever does go, that is a major version with its own notice, not a footnote here.

### Also new since 0.12.0

- **SPDX 3.0.1 records vulnerabilities.** `--vulnerabilities` findings used to reach CycloneDX
  only, and an SPDX run warned it was dropping them. They now come out as `security_Vulnerability`
  elements with CVSS, CISA KEV and VEX assessments through SPDX 3's security profile. SPDX 2.3
  still has nowhere to put them and points you at `--spec-version 3.0`.
- **`uses: millsks/pixi-sbom@v1`** follows the newest 1.x.y release, so the action can be pinned to
  a major and left alone.

### Upgrading from 0.12.0

Nothing to do. Change `@v0` to `@v1` in a workflow when convenient — `@v0` keeps resolving to the
newest 0.x release, which is not this one, so it will stop receiving updates.
